# 2026-10-14 — segregation-of-duties transition conditions (hardening PR 1)

**Session type:** Code
**Branch:** `feat/PLAT-hardening-sod-condition-operators`

- Adds `actor_not_creator` and `actor_not_prior_actor` (optional `states`) as transition-only condition operators in a `TransitionConditionTree` superset of `ConditionTree`, so automation rules, which have no actor and share `ConditionTree`, cannot use them and their schema guards are untouched. Spec: `docs/specs/segregation-of-duties.md`.
- `executeTransition` loads the actor context (creator, prior acting users) after the row lock; the prior-actor query runs only when a tree needs it. Rules fail closed for an unidentified actor. `getAvailableTransitions` takes the actor id so the offered list matches the guard.
- Transition create and update routes now validate `conditions` (`TransitionConditionsSchema`) instead of `z.unknown()`, so a typo is a 400. Compile-time guards keep the schema and the engine type in sync.
- Real-Postgres tests run as `app_user`. Mutation-checked: making `actor_not_creator` always true, or letting an unidentified actor through, each fails the tests that should catch it.
- Not in this PR: the guarded state override and the removal of the direct state-set paths (PR 2), and the `vendor-approval` seed change (PR 3), which needs the override first so `admin` is not left with no way to act.
- A security-reviewer pass found two real bypasses, both fixed and covered by tests that fail if the flaw is reintroduced: (1) the prior-actor query classified comments by caller-writable `metadata`, so a transition sent with `{"type":"comment"}` stopped counting as acting (it now uses `from_state <> to_state`, which the server sets; this also stops tag, severity and attachment events counting as acting); (2) an API-key identity (`apikey:<id>`) satisfied every actor rule, so a creator could approve through a key (non-user identities now fail closed). Also fixed: `not(actor rule)` failed open for an unidentified actor (now rejected at write time and never satisfied by the engine, with a positive `actor_is_creator` for "only the creator"); the write-time depth limit ran after a full lazy parse (the schema is now built to a fixed depth); the idempotency replay query lacked an explicit tenant filter (pre-existing, added).
- Audit: rule changes were not recorded. Added `workflow.transition_conditions_updated` (migration 0145, numbered after the open #928's 0144; renumber one of them if both land) across create, update, delete and canvas deletion.
- Known and left for later PRs: the idempotent replay returns an earlier event regardless of caller (pre-existing; no state change), and the seed worker passes a plain `db` handle so the actor context is read outside a lock (it uses `system`, which fails closed on actor rules, so a seeded segregation workflow needs the override from PR 2).
- A second review pass confirmed the five fixes and raised: a rule's `states` was never checked against the workflow (a typo or a rename left a rule that blocks nobody) and the schema's union re-parsed children on every failed branch. Fixed: `states` must name real steps on create and update, and renaming or deleting a step that a rule names is refused (past events keep their old names, so a rename would silently stop matching); the schema is now a discriminated union per level, measured at about 0.5-0.8 microseconds per node whether the tree is valid or not (a 2.4 million node tree parses in 1.3s; a 1 MB body is about 25ms), so the amplification the review estimated is gone.
- The spec now has a Known limits section. The rules guard transitions executed through the engine; other ways of changing a record's state are covered by the guarded-override follow-up (PR 2), which is why the seed workflow waits for it.
