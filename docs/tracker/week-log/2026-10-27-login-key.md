# 2026-10-27 — Login link carries a random key, and the login card names the org (R13, revised)

**Session type:** feature change (docs/specs/multi-org-sandbox.md R13, Phase 6, T41–T48)
**Branch:** `feat/login-org-branding` (local, on top of PR #1077; the PR opens after #1077 merges)

- **Why.** The first version put the tenant's slug in the link (`/login?org=local-org-6153`). The
  slug is the org's name plus four digits, fixed at creation, so it showed the old name after a
  rename and could be guessed from a company name (ten thousand suffixes). The link now carries a
  random key that has nothing to do with the name.
- **Key.** Migration `0162_tenant_login_key`: `tenants.login_key`, 16 lowercase hex characters,
  unique, CHECK on its format, and a second CHECK that only a sandbox can hold one (a real tenant can
  never be reached through it). Existing sandboxes are backfilled from `gen_random_uuid()` in the
  migration; new ones get 8 random bytes from the provisioning worker. It never changes. The migration
  also grants `platform_admin_role` `SELECT (login_key)` and revokes the `SELECT (slug)` that 0161
  had added, since nothing reads the slug now (0161 itself stays as history).
- **Lookup.** `GET /public/org-branding/:key` looks up by `login_key` (still only an `active` sandbox),
  validates 16-hex before reading the database, and answers every miss with the same `404`, including
  a readable slug or a tenant id. It never returns the key.
- **Platform admin.** `loginKey` replaces `slug` on the sandbox view and the handover; the row menu,
  detail panel, creation reveal, CSV and clipboard text carry `/login?org=<key>`. A sandbox with no key
  (impossible after the migration, possible mid-deploy) simply shows no link.
- **Login page.** The card's "OpenWind / Sign in" breadcrumb now names the sandbox on its link, as
  does the browser tab title (put back on leaving). Both stay generic while the lookup runs and on every
  miss; the breadcrumb's brand is held invisible while loading.
- **Effect on existing links.** The one handed-over link that used a slug stops working; the dashboard
  shows the new one.
- **Not built.** Regenerating or revoking a key (a leaked link cannot yet be revoked); Zitadel's own
  sign-in screen still shows after pressing sign-in.
- **Tests.** Unit: the lookup (keys, ten malformed shapes, slug and tenant-id values, never echoing the
  key), the view and handover, the worker (16-hex, distinct per sandbox, unrelated to name), the link
  helper, the login page (breadcrumb, tab title, misses, slug refused), the hook, the row menu and
  panel with and without a key. Isolation (real Postgres, throwaway container): format, uniqueness and
  sandbox-only CHECKs, the backfill statement on key-less sandboxes, `platform_admin_role` reads the key
  but neither the slug nor `config`/`plan`/`zitadel_org_id`, cannot change it; the public lookup's
  misses are byte-identical and a slug or tenant id never resolves.
- **Security review.** No blocking or high findings. Key quality (60 to 64 random bits behind a 30 per
  minute per-IP limit), the one-shape 404, the grants and the migration order all held. Accepted and
  recorded in the spec's R13: the key lives in the address bar and history (no explicit
  `Referrer-Policy`; `same-origin` at the proxy is optional); a purged sandbox's tombstone keeps its
  key (never answered, no personal data, clearing it needs another grant); a hostile sandbox name could
  carry bidirectional characters into the tab title (platform-admin only; stripping at write time is a
  follow-up). Operational note: the migration takes a brief `ACCESS EXCLUSIVE` lock on `tenants` for
  its constraints, so apply it when no long tenant transaction is running; the table is small.
