## Notes carried over from `/spec-review` (do not re-litigate during implementation)

- The unique index is scoped to `WHERE ... AND status = 'success'` **on purpose** — a blanket `WHERE transition_event_id IS NOT NULL` index was the original design and is now known-wrong (§B). If an implementer is tempted to "simplify" it back to a blanket index, re-read spec §V item 2 first. (Corrected from `'completed'` to `'success'` post-review, PR #372 H1 — `executor.ts` never writes the literal string `'completed'`.)
- **M1 (PR #372 review):** the idempotency-replay short-circuit path in `executeTransition` (`engine.ts`) generates a _fresh_ `transitionEventId` on every replay, distinct from the one associated with the original execution. T4's dedup check keys on `(ruleId, transitionEventId)` and will find no match for a replay, re-running the automation rule every time the same idempotency key is replayed. Inert today (Phase 1 — nothing reads `transitionEventId` yet), but T4's implementer must account for this before shipping Phase 2 dedup, not discover it in production.
- `transitionEventId` is threaded as an **explicit function parameter**, not embedded in `TransitionRequest` or `followUpEvent`. If an implementer finds themselves adding a field to either of those, that's a sign the T3 approach has drifted from the spec — stop and recheck against §I.
- Security-relevant: this changes recursion/DoS-bounding logic (`MAX_DEPTH`) and adds a new advisory-lock code path. `/security-review` is warranted before merge per `security.md`'s general rule, independent of whether this PR touches auth/routes/tables in the narrower sense.
