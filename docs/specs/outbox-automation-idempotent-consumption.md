# Outbox: unconditional write + idempotent automation consumption (#143)

> automation-triggered transitions reach outbox_events again, w/o reintroducing #120 (double-exec / unbounded recursion). Unblocks ADR-009 Decision #3 (connector webhook gateway reads the outbox).

status: done
created: 2026-08-09

## §G Goal

- every `workflow.transitioned` transition writes to `outbox_events`, regardless of `triggeredBy` — no consumer (connector delivery, ADR-009; future outbox consumers) silently misses automation-caused transitions
- automation's own rule execution still fires exactly once per (rule, transition) — sync in-process path and async outbox→worker path for the same transition must not both run a rule's actions
- MAX_DEPTH recursion bound (executor.ts) still holds for the async path — currently dead code, must become live correctly

## §I Interfaces

**`TransitionRequest`** (`packages/workflow-engine/src/types.ts`) — no new field needed; `depth` already exists (line 88-91). Gap is purely that `engine.ts` never reads it into the outbox payload.

**`WorkflowTransitionedEvent` / `WorkflowTransitionedV1Schema`** (`event-schemas.ts`) — `depth` already declared optional. Add:

```ts
transitionEventId: string; // uuid, always set — the identity of THIS transition, stable across the sync in-process path and the async outbox→worker path for the same transition
```

Derived once per `executeTransition` call (e.g. `crypto.randomUUID()` generated inside the same function that builds `outboxPayload`, independent of `triggeredBy` — cheapest option, no dependency on `workflow_events`' own row id). **`executeTransition` must also return `transitionEventId`** as a new field on its result object — its current return shape (`id`/`instanceId`/`workflowId`/`fromState`/`toState`/`triggeredBy`/`actorId`/`comment`/`metadata`/`createdAt`, `engine.ts:341-352`) has no room for it today.

**Threading (revised after `/spec-review` — see §B):** `transitionEventId` crosses the sync/async boundary as an **explicit function parameter**, mirroring how `depth` and `outboxEventId` already solve exactly this problem in `executeAutomationRules(db, tenantId, event, depth, redis, outboxEventId)` — not solely embedded in the event payload. Concretely: `transition.ts`'s `executeTransitionAction` captures `workflowEvent.transitionEventId` from `executeTransition`'s return value and passes it as a new parameter into `executeAutomationRules`/`runAction`, alongside `depth + 1` and `outboxEventId`. `apps/worker/src/automation-worker.ts` (async path) extracts `transitionEventId` from the outbox payload the same way it already extracts `depth` via `readDepth()`, and passes it through the same new parameter. `TransitionRequest` itself needs no new field — the gap is entirely on the return/threading side, not the request side.

**`automation_executions`** (`packages/db/src/schema/automation-engine.ts`) — new migration:

```sql
ALTER TABLE automation_executions ADD COLUMN transition_event_id uuid;
CREATE UNIQUE INDEX automation_executions_rule_transition_success_idx
  ON automation_executions (rule_id, transition_event_id)
  WHERE transition_event_id IS NOT NULL AND status = 'success';
```

**Scoped to `status = 'success'` — deliberately not a blanket unique index (revised after `/spec-review`).** A blanket `WHERE transition_event_id IS NOT NULL` index would permanently block retry of a failed execution: today's code intentionally persists `status: 'failed'` rows (written via the outer `db` specifically so they survive an inner-transaction rollback, `executor.ts`'s comment above the try/catch) rather than deleting them, so a later retry attempt for the same key must be allowed to insert a fresh row. This index is a **defensive backstop**, not the primary dedup mechanism — see §I's concurrency-control entry below for the actual guard. Nullable/partial, same pattern as `workflow_events_instance_idempotency_idx` (migration 0004); non-transition-sourced executions keep `transition_event_id = NULL` and never touch this index.

**Concurrency control (new, added after `/spec-review`):** before inserting the `status: 'running'` row or running any action, when `transitionEventId` is present, acquire an xact-scoped advisory lock keyed on `(ruleId, transitionEventId)` (e.g. `pg_advisory_xact_lock(hashtextextended(rule_id || ':' || transition_event_id, 0))`) — auto-released on commit or rollback, no explicit unlock needed. Immediately after acquiring, `SELECT` for an existing `status = 'success'` row for that key; if found, skip this rule entirely (no new `automation_executions` row, no actions run, lock released on the enclosing transaction's end). Otherwise proceed with today's insert-running → run-actions → update-status flow, unchanged. The lock is what actually prevents the race (two concurrent attempts serialize on it); the partial unique index above only catches a bug in this logic, it doesn't substitute for it.

## §R Requirements

R1: `engine.ts`'s outbox write is unconditional — the `if (triggeredBy !== "automation")` guard is removed.
✓ a `triggeredBy: "automation"` transition produces a `workflow.transitioned` outbox row (currently: zero rows)
✓ existing `triggeredBy: "user"/"api"/"system"` behavior unchanged (still one outbox row each)

R2: every outbox-routed `workflow.transitioned` payload carries the transition's `depth` and a stable `transitionEventId`.
✓ `outboxPayload.depth === request.depth` for every `triggeredBy` (today: field exists on the type, never populated)
✓ `outboxPayload.transitionEventId` is a fresh uuid, generated once per `executeTransition` call, identical whether read back via the sync in-process path or the async worker path for the same transition

R3: a rule's actions execute at most once per **completed** `(ruleId, transitionEventId)` pair; a prior failed or incomplete attempt never blocks a later retry for the same pair.
✓ `transitionEventId` reaches `executeAutomationRules`/`runAction` as an explicit parameter on both the sync in-process path (from `executeTransition`'s return value) and the async outbox→worker path (extracted from the outbox payload, mirroring `readDepth`) — not solely embedded in the event object
✓ before running a rule's action(s), an advisory-lock-guarded check for an existing `status = 'success'` row for `(ruleId, transitionEventId)` skips execution entirely (not just logging) if found
✓ a rule execution that previously failed for a given `(ruleId, transitionEventId)` can be retried and complete successfully on a later attempt for the same pair
✓ two concurrent attempts for the same `(ruleId, transitionEventId)` — sync-vs-async, or two async workers — produce exactly one completed execution and one skip, never two completions
✓ non-transition-sourced executions (`transitionEventId` undefined) are unaffected — existing behavior for `entity.created`/`entity.assigned` etc. unchanged

R4: `MAX_DEPTH` bounding (executor.ts, currently 10) applies correctly to automation-triggered transitions reaching automation via the async outbox→worker path.
✓ an automation-triggered transition whose in-process recursion is already at depth D produces an outbox row with `depth: D+1` (via R2), and if that row is later consumed async, `executor.ts` enforces `MAX_DEPTH` against `D+1`, not `0`

## §V Invariants

- outbox write in `engine.ts` is unconditional on `triggeredBy` — the "skip on write" pattern from PR #139 must never come back; dedup lives in the consumer (R3), never in the producer
- `automation_executions`'s new unique index is partial on `WHERE transition_event_id IS NOT NULL AND status = 'success'` — never a blanket `WHERE transition_event_id IS NOT NULL` index. `status: 'failed'` rows are deliberately persisted (not deleted) by existing code specifically so they survive an inner-transaction rollback; a blanket index would permanently block any retry of a failed execution
- the completed-status check in R3 happens **before** any action side effect runs, never after — an after-the-fact dedup (like `notify.ts`'s current pattern) only prevents duplicate _logging_, not duplicate side effects, for actions that aren't naturally idempotent (e.g. `transition`, `create_child`)
- `transitionEventId` is generated inside `executeTransition` itself, not derived from `workflow_events`'/`outbox_events`' own row ids — those ids differ between the row a rule's in-process call is "rooted at" and the new row `engine.ts` writes for the transition it just performed; only a value threaded explicitly through both paths stays identical
- `transitionEventId` flows as an **explicit function parameter** alongside `depth`/`outboxEventId` through both the sync (`transition.ts`) and async (`automation-worker.ts`) call chains — never solely embedded in the event/payload object. `executeTransition`'s return value, not `TransitionRequest`, is where the sync path picks it up
- the completed-status check and the running-row claim happen inside a single advisory-lock-guarded scope (`pg_advisory_xact_lock`, keyed on `(ruleId, transitionEventId)`) so two concurrent attempts for the same pair serialize instead of racing — the partial unique index is a backstop against a bug in this logic, not the primary mechanism
